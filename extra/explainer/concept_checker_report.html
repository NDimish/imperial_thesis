Modules · ConceptChecker

A concept-level, deterministic checker — built, tested on 5 real files, and honestly evaluated

Every existing checker in this project (AlignScore, FactKB, Kdbe, SummaC) scores isolated sentences against a whole other document using models trained on generic text. This module tries a structurally different, still fully deterministic approach: compare UMLS concepts and their negation status directly, reusing the same matcher and ConText machinery already built for this project's condensers. It works, sometimes -- and the real 5-file test surfaced exactly why it isn't there yet.

Date 2026‑08‑05 New file Modules/concept_checker.py Tested on 5 real transcript/SOAP pairs, real ground-truth labels

Why a different architecture, staying fully deterministic

A separate discussion this session concluded that per-sentence isolated-context NLI scoring (what every other checker here does) has three structural weaknesses for this task: it fragments conversational context, it's trained on the wrong domain (news/Wikipedia-style entailment, not clinical shorthand), and it can't synthesize a claim scattered across several transcript turns into one SOAP line. A whole-document LLM was the obvious fix for all three -- but non-determinism and an external API dependency ruled that out here. This is the deterministic alternative: instead of comparing sentence text, compare UMLS concepts.

Concepts are matched by CUI (UMLS's concept ID), not surface text, so "smoking" and "Nil smoking" resolve to the same underlying concept regardless of register -- directly targeting the domain-mismatch problem, since a CUI is phrasing-independent by construction. Each concept's assertion status (negated / affirmed / hypothetical) comes from medspacy's ConText, the same algorithm already validated for this project's condensers -- and SOAP notes are exactly ConText's intended domain ("denies fever", "nil smoking"), unlike the transcript side, where this project already found and fixed a real ConText/question mismatch.

The comparison logic: a concept is a hallucination if it's asserted in the SOAP note at some polarity with no matching CUI+polarity anywhere in the transcript. It's an omission if the reverse is true. Matching on CUI+polarity together, not just CUI, means "I smoke" and "I don't smoke" -- which can score deceptively close on raw embedding cosine similarity, since they're both "about smoking" -- are correctly treated as different facts.

First smoke test

One file, 75 flagged items, and a familiar problem

Running the first working version on a single file (prim1.txt) found 75 flagged errors -- an implausibly high count. Inspecting them found the same coincidental-UMLS-collision problem already documented for this project's condensers, but worse here: words like "hand" (a real T023 Body Part entry), "life" (a real T060 Diagnostic Procedure entry), "said"/"times" (real T047 Disease/Syndrome entries) were being matched as clinical concepts. Checked directly -- every one is an exact similarity=1.0 match, not a borderline fuzzy one, so raising the match threshold wouldn't have helped.

Two fixes applied, in order

1. Ngram-aware collision check (75 → 71 errors): checking both the matched canonical UMLS term and the raw surface text against the existing denylist, not just the term -- the same fix found and reverted for the condensers (there, it cost real recall; here, a junk match directly manufactures a spurious error, so the tradeoff runs the other way).

2. A checker-scoped junk-concept denylist (71 → 40 errors): kept local to concept_checker.py, not added to the shared list the condensers use, specifically to avoid reopening their recall cost. Deliberately narrow -- "smoker", "vitamins", "triggers", "stools", "bowels", "back", "food", "eating" all also looked like noise in this same file, but were kept out of the denylist since they're genuinely clinical concepts; their appearance as false positives is a symptom of a different problem (see below), and denylisting them would have hidden it instead of fixing it.

✓ 75 → 40 flagged items on the same file, all from principled, tested fixes -- not by discarding awkward results.
Real 5-file test

The honest result: it works sometimes, and the measurement says otherwise

Read at face value, this is a clear loss against every existing checker. It would be dishonest to stop there without checking why -- especially since the smoke test had just shown the remaining flags looked plausible, not random.

What was actually going on Cross-checking the "missed" (false-negative) real labels against the "added" (false-positive) flags in the same files found several clear matches that the scoring simply couldn't see:
Real label (missed)prim10.txt: “Brief episode of haematuria, now resolved.”
This checker flagged (added)“haematuria (negated)”
Real label (missed)prim11.txt: “Lives with wife and children.”
This checker flagged (added)“lives (affirmed)”
Real label (missed)prim13.txt: “Had visual aura before onset of headaches — zigzag lines in field of vision.”
This checker flagged (added)“visual aura (affirmed)” and “field of vision (affirmed)”
These are very plausibly the same real errors, described in a structurally different vocabulary. Modules/evaluate.py's label matcher was built for the other checkers' output style (a verbatim sentence, close enough in phrasing to substring-match the label) -- and for hallucination-type predictions specifically, it only does substring matching, with no embedding-similarity fallback (that fallback exists only for omission-type predictions, and was itself only validated on one earlier example). A concept-and-polarity output like "haematuria (negated)" was never going to substring-match a full sentence, no matter how correct the underlying detection was.

That explains some of the false positives, not most of them. Scanning the rest of the 344 flagged items, the large majority are still genuine noise -- "usually", "probably", "definitely", "maybe", "history", "confirm", "worry", "call", "screen", "thought" -- the same coincidental-UMLS-collision problem the single-file smoke test's denylist was built from, except at 5-file scale it's clearly a much longer tail than one file could ever reveal. This is the same conclusion this project already reached for the condensers, now confirmed a second time in a different module: a hand-typed denylist, however well-reasoned each individual entry is, does not scale to covering this problem on its own.

Honest verdict

Real, but not yet usable as-is

Two separate things are true at once. The architecture is sound and demonstrably catches errors the per-sentence checkers structurally cannot -- the haematuria, "lives", and visual-aura cases above are all real detections invisible to raw substring/NLI-on-isolated-sentences matching, because they only make sense once you already know "haematuria" is the same concept whether it's called that or described conversationally. But this specific first implementation isn't ready to trust: precision is far too low to use standalone, and worse, the current evaluation methodology can't even measure this checker fairly, since it was built around a different checker's output shape.

Two concrete next steps, not vague caveats:

  1. A compatible evaluation adapter. Either extend Evaluate._texts_match to also try embedding-similarity matching for hallucination-type predictions (not just omission-type), or give concept-style outputs their own comparison path, so a correct detection in a different vocabulary isn't automatically scored as wrong.
  2. A systematic precision fix, not more denylist entries. The same principled levers already proven for the condensers this session -- narrowing accepted semantic types, or a stricter matcher instance tuned specifically for 1:1 fact comparison rather than reused as-is from the condensers' recall-first configuration -- are the right next move, not continuing to hand-expand a list that a 5-file test already showed doesn't generalize from 1 file.

All numbers above come from real runs of main.py over the same 5 labeled files (prim1, 10–13) used to calibrate this project's other checkers, scored through the same unmodified Evaluate class. The evidence pairs quoting "missed" and "added" entries are read directly from Logs/evaluate_ConceptChecker_*.log, not reconstructed after the fact.
