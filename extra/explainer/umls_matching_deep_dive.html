Medical condensor · umls_matching.py & umls_checker.py

How UMLS matching actually works, why its precision sits at 0.518, and what happens when fuzzy matching is switched off

Every condenser and checker in this project depends on one shared component to answer "is this span a real clinical concept": Medical condensor/umls_matching.py, built on QuickUMLS. This had never been measured directly until now. This walks through exactly how it works, quantifies precisely why it's wrong roughly half the time using a hand-labeled 1177-term gold standard, then re-runs the whole evaluation with fuzzy matching disabled to see what that actually buys.

How the matching actually works

QuickUMLS is an approximate-string-matching library over the UMLS Metathesaurus — a merged vocabulary of SNOMED CT, MeSH, RxNorm, and dozens of other clinical terminologies, containing millions of terms. Given a span of text, it looks for windows of words whose character-ngram profile is similar enough (by Jaccard similarity) to some UMLS term, and returns every sufficiently-similar candidate along with that term's CUI (Concept Unique Identifier) and semantic type(s).

This project wraps one shared, tuned matcher instance around that in umls_matching.py, so every condenser and checker answers "is this real" the same way instead of drifting separately:

THRESHOLD = 0.75          # similarity floor for a fuzzy match to count
MIN_MATCH_LENGTH = 4       # shortest span QuickUMLS will consider
ACCEPTED_SEMTYPES = {      # 20 semantic types (of ~130 in UMLS) allowed through
    "T023", "T029", "T031", "T033", "T034", "T037", "T040", "T041",
    "T046", "T047", "T048", "T059", "T060", "T061", "T121", "T184",
    "T191", "T195", "T200", "T201",
}
GENERIC_WORD_DENYLIST = {  # 21 words: real UMLS entries with no clinical use here
    "start", "well", "good", "fine", "right", "help", "birth",
    "like", "think", "mean", "talk", "don't know", "i don't know",
    "nothing", "else", "aware", "symptom", "symptoms", "problem",
    "problems", "medical history",
}

Three functions sit on top of the matcher, each used differently by the three condensers:

  • has_real_concept(text) — true/false, "does this turn/sentence contain at least one real clinical concept". QuickUMLSCondenser uses this directly per turn: keep the turn if true, drop it if false.
  • get_real_concept_spans(text) — character offsets for every real match. MedspacyCondenser and NegspacyCondenser inject these spans as spaCy entities so their assertion-detection pipelines (ConText / negex) have something concrete to check negation/hypothetical status against — neither medspacy nor negspacy ships its own UMLS linker, so this is the only source of "which words are clinical" they have.
  • _is_common_match(m) — checks both QuickUMLS's matched canonical term and the actual surface text (ngram) against the denylist, since they can differ (see below).

The threshold and denylist values above aren't arbitrary — each was arrived at from a real full-dataset regression documented directly in the file's comments: raising the threshold to 0.85 (to kill false positives) instead cost real matches like "smoke"→"smoker" (similarity 0.75) and "peanuts"→"peanut" (0.80); the denylist exists because words like "well" and "start" are exact (similarity=1.0) UMLS entries, immune to any threshold.

How precision was measured

umls_checker.py runs the real matcher (same threshold, same semtypes) over 20 real transcript/SOAP pairs, aggregates every match by unique (term, semtypes) pair (annotating 7406 raw occurrences by hand isn't tractable; annotating the 1177 unique pairs they collapse to is), and asks: for each one, is this a genuine clinical concept in this dataset, or a coincidental collision? Every one of the 1177 was hand-judged against the same standard used to build the existing denylist — applied completely and systematically this time, not just to whatever happened to surface as an obvious problem before.

Recall was not measured — that would require reading raw text for concepts the matcher never found at all, a fundamentally different and much slower annotation task. This is a precision-only evaluation, stated as a scope limit rather than left implicit.

Root causes, with numbers

Why precision is only 0.518

Of the 1177 unique matches, 503 (43%) are false positives — 4025 of the 7406 total labeled occurrences. The existing denylist catches only 18 of those 503 terms (880 occurrences); the other 485 terms, 3145 occurrences, are completely unfiltered. That gap is most of why precision sits where it does. Three distinct mechanisms are responsible:

1. UMLS genuinely contains ordinary English words as real clinical entries

These aren't matching errors — QuickUMLS found a real, exact (similarity=1.0) CUI. The vocabulary is just enormous enough that everyday conversational words collide with it constantly:

2. Fuzzy-match corruption at the 0.75 boundary

The single biggest offender in the entire dataset: "right" fuzzy-matches the completely unrelated canonical terms "bright" (231×) and "fright" (227×) — 458 occurrences from one collision. The existing denylist already flags "right" itself, but never covers what it fuzzy-matches into, since those are different canonical terms. Same pattern elsewhere: metforming↔metformin, penicilli↔penicillin, helpin↔helping, shearing↔hearing.

3. Broad semantic types are inherently promiscuous

T033 ("Finding") and T201 ("Clinical Attribute") are catch-all categories that also cover meta-words with zero discriminating content: symptom(s), problem(s), plan, diagnosis, treatment, sign. These are technically correct UMLS lookups — just useless for telling two documents apart.

The transcript/SOAP split (0.420 vs 0.641) is exactly what these three mechanisms predict: SOAP notes are already clinician-written shorthand, so most spans really are clinical; transcripts are conversational spoken English transcribed verbatim, exactly where a fuzzy general-purpose matcher collides most.

Experiment

What happens when fuzzy matching is switched off

QuickUMLS has no separate "exact match" flag — its threshold parameter is the fuzzy-matching knob, from 0.0 (anything) to 1.0 (only spans whose character-ngram profile is identical to a UMLS term). Setting it to 1.0 is what "no fuzzy matching" means in this API. Re-ran umls_checker.py extract --threshold 1.0 across the same 20 files into a separate directory, propagated the existing 1177-term human labels onto whatever survived (every match at threshold=1.0 is a subset of what existed at 0.75, so the vast majority already had a label), hand-labeled the 23 newly-surfaced multi-word phrases ("family history", "type 2 diabetes", "rheumatoid arthritis", etc. — longer exact phrases that beat out a shorter fuzzy candidate once fuzzy competition was removed), then re-scored.

"Accuracy" is not a separate number from precision here: this evaluation only ever sampled and labeled things the matcher did match (true positives + false positives). It never sampled the spans the matcher skipped, so there are no labeled true negatives or false negatives to fold into a real accuracy = (TP+TN)/(TP+TN+FP+FN). Reporting it anyway, with this caveat attached rather than a number that looks independent when it isn't: accuracy over the labeled sample = 0.512, identical to raw precision.

The 27.8% drop in total matches found is the tradeoff, and it's the same one already documented in umls_matching.py's own comments: threshold=0.75 exists specifically because raising it to 0.85 was already tested and found to cost real matches ("smoke"→"smoker"=0.75, "peanuts"→"peanut"=0.80, "allergic"→"allergican"=0.75) — all of which would also be lost at threshold=1.0. This experiment confirms that same precision/recall tradeoff on the measurement side: exact-only matching is meaningfully more precise, but not free.

This change was NOT applied to the live matcher — umls_matching.THRESHOLD (used by all three condensers and every checker) is untouched at 0.75. The experiment ran through a threshold override in umls_checker.py alone, specifically so it could be measured as its own question without regressing the condensers' already-tuned recall.
