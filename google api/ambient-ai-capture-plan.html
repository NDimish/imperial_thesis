Planning doc · browser capture pipeline

Capturing an ambient AI scribe's transcript + note, and watching it for drift

A practical plan for a Chrome extension that sits on top of an ambient AI documentation tool (the kind that listens to a consult and drafts a SOAP note), captures the transcript and both the AI's raw draft and the clinician's edited final version, ships that to a small server, and surfaces it on a dashboard — with an eye toward the actual goal: noticing if the underlying model's quality degrades over time.

1 · Overview / architecture

Four pieces, each independently simple. The extension never talks to your server directly from the page context — everything routes through the background service worker, which sidesteps the target site's Content-Security-Policy and CORS restrictions.

(transcript + note in the DOM)
→
Content script
observes DOM, snapshots text
→
Background service worker
batches, adds auth header

Your server
Flask + SQLite, /events

edit-rate trend, drill-down

Everything below assumes you're building this for your own research/monitoring use against a tool you (or your institution) already has legitimate access to — this is not a guide to scraping a product you don't have rights to use.

2 · Building the extension

Manifest V3, the current Chrome extension format. Three files to start: manifest.json, a content script that runs inside the ambient AI app's page, and a background service worker that relays captured data out.

manifest.json

manifest.json
{
  "manifest_version": 3,
  "name": "Ambient Note Capture",
  "version": "0.1.0",
  "description": "Captures transcript + generated note for research monitoring.",
  "permissions": ["storage", "scripting"],
  "host_permissions": [
    "https://*.your-ambient-ai-vendor.example/*",
    "http://localhost:5000/*"
  ],
  "background": { "service_worker": "background.js" },
  "content_scripts": [
    {
      "matches": ["https://*.your-ambient-ai-vendor.example/*"],
      "js": ["content.js"],
      "run_at": "document_idle"
    }
  ]
}

content.js — DOM-scraping version
// Selectors are illustrative -- inspect the real page and swap these in.
const NOTE_SELECTOR = '[data-testid="generated-note"]';
const TRANSCRIPT_SELECTOR = '[data-testid="live-transcript"]';
const SIGN_BUTTON_SELECTOR = '[data-testid="sign-note-button"]';

let baselineNote = null;   // the AI's first, unedited draft
let baselineCapturedAt = null;

function snapshotNote() {
  const el = document.querySelector(NOTE_SELECTOR);
  return el ? el.innerText : null;
}
function snapshotTranscript() {
  const el = document.querySelector(TRANSCRIPT_SELECTOR);
  return el ? el.innerText : null;
}

// Fires on every DOM change in the note panel -- take the FIRST
// non-empty snapshot as the untouched AI draft (see §4).
const observer = new MutationObserver(() => {
  const current = snapshotNote();
  if (current && baselineNote === null) {
    baselineNote = current;
    baselineCapturedAt = Date.now();
  }
});
observer.observe(document.body, { childList: true, subtree: true, characterData: true });

// Fires when the clinician finalizes the note -- this is the "after" state.
document.addEventListener('click', (e) => {
  if (!e.target.closest(SIGN_BUTTON_SELECTOR)) return;
  chrome.runtime.sendMessage({
    type: 'NOTE_FINALIZED',
    payload: {
      sessionId: crypto.randomUUID(),
      transcript: snapshotTranscript(),
      noteBefore: baselineNote,
      noteAfter: snapshotNote(),
      capturedAt: baselineCapturedAt,
      finalizedAt: Date.now(),
    },
  });
});
background.js
const API_URL = 'http://localhost:5000/events';
const API_KEY = 'dev-only-key-replace-me';  // load from chrome.storage in real use

chrome.runtime.onMessage.addListener((message) => {
  if (message.type !== 'NOTE_FINALIZED') return;
  fetch(API_URL, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'X-API-Key': API_KEY },
    body: JSON.stringify(message.payload),
  }).catch((err) => console.error('capture upload failed', err));
});

3 · What you'd need to connect this

  • Host permissions in manifest.json for both the ambient AI app's domain (to inject the content script) and your own server's domain (so the background worker's fetch isn't blocked).
  • Routing writes through the background worker, not the content script. A content script's fetch is subject to the target page's own Content-Security-Policy, which will often block a request to an origin the page didn't itself whitelist. The background service worker isn't a page at all, so it isn't bound by that CSP.
  • An API key or token for your own server — a static key in chrome.storage is fine for a prototype; swap for a per-install token or OAuth if this ever handles real patient data.
  • De-identification before anything leaves the browser if you're anywhere near real patient data: strip or hash name/DOB fields client-side, and treat this as PHI-handling that needs IRB/institutional sign-off — not a detail to defer. Everything in this project's own prim57 dataset is synthetic for exactly this reason.
  • A vendor developer account, if you go the API/webhook route instead of DOM scraping — most ambient scribe vendors (used in EHR integrations) have one; worth asking before building the scraping path.

Ask first, scrape second. Injecting a content script into a SaaS product's pages to read data back out sits in a legal and ToS gray area even when you have a legitimate account — check the vendor's terms of service and, ideally, tell them what you're doing. A developer API is the version of this that doesn't need a caveat.

4 · Tracking edits, and where

An "edit" here means: the difference between the AI's first, untouched draft and whatever the clinician actually signs. Two snapshots, one diff — the trick is reliably capturing the first one before anyone touches it.

Where the "before" snapshot comes from

The MutationObserver in §2 takes the first non-empty read of the note panel as baselineNote and then stops updating it — every later mutation is an edit, not a new baseline. This is the one part of the whole pipeline worth testing carefully: if the ambient AI streams the note in token-by-token, "first non-empty" will catch a half-written sentence, not the finished draft. In that case, debounce — wait for a short quiet period (e.g. 1.5s with no further mutations) before locking in the baseline, rather than taking the very first paint.

Where the "after" snapshot comes from

Either the explicit sign/finalize action (cleanest — one clear "this is final" event), or, if there isn't one, a periodic snapshot (every 30–60s) so you get an edit trail across the session rather than one before/after pair. The periodic version is more work to diff (many snapshots, not two) but tells you when in the encounter edits happen, which the single before/after pair can't.

Where the diff/categorization happens

Do the raw text diff on the server, not in the extension — keep the extension dumb (snapshot + ship), keep the logic somewhere you can iterate on without re-publishing a browser extension. difflib.SequenceMatcher (stdlib) is enough for a first pass at an edit ratio; for something more clinically meaningful, run this project's own Modules/note_extractor.py or Modules/high_risk_checker.py against noteBefore and check whether the clinician's actual edit overlaps the spans it flagged. That turns every real signed note into a free, continuous validation sample for the checker itself — the same question this whole project has been answering by hand on prim57, except live and ongoing.

This is the single highest-leverage integration point in the whole pipeline: every edited note is a natural experiment in "was the checker's flag right." A clinician deleting a sentence the checker flagged as a hallucination is about as good a ground-truth signal as this project's manual labeling sessions produced, and it costs nothing extra to collect once the capture pipeline exists.

5 · A pseudo server for the extension to save data to

For a prototype, Flask + SQLite is the whole stack — no infrastructure to stand up, and it matches this project's existing Python tooling. One route to receive events, one to serve the dashboard.

server.py
from flask import Flask, request, jsonify, render_template
import sqlite3, difflib, datetime, os

app = Flask(__name__)
DB_PATH = "capture.db"
API_KEY = os.environ.get("CAPTURE_API_KEY", "dev-only-key-replace-me")

def get_db():
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row
    return conn

def init_db():
    with get_db() as conn:
        conn.execute("""
            CREATE TABLE IF NOT EXISTS sessions (
                id TEXT PRIMARY KEY,
                transcript TEXT,
                note_before TEXT,
                note_after TEXT,
                edit_ratio REAL,
                captured_at TEXT,
                finalized_at TEXT
            )
        """)

@app.route("/events", methods=["POST"])
def capture_event():
    if request.headers.get("X-API-Key") != API_KEY:
        return jsonify({"error": "unauthorized"}), 401
    data = request.get_json()
    before, after = data.get("noteBefore", ""), data.get("noteAfter", "")
    edit_ratio = 1 - difflib.SequenceMatcher(None, before, after).ratio()
    with get_db() as conn:
        conn.execute(
            "INSERT OR REPLACE INTO sessions VALUES (?,?,?,?,?,?,?)",
            (data["sessionId"], data.get("transcript"), before, after, edit_ratio,
             datetime.datetime.utcfromtimestamp(data["capturedAt"]/1000).isoformat(),
             datetime.datetime.utcfromtimestamp(data["finalizedAt"]/1000).isoformat()),
        )
    return jsonify({"status": "ok"})

if __name__ == "__main__":
    init_db()
    app.run(port=5000)

Two things worth doing before this touches anything real: put it behind HTTPS (a local ngrok tunnel is enough for testing against a vendor app that requires secure origins), and swap the static API key for a per-install token once more than one machine is reporting in.

6 · A basic dashboard, server-side

One more route on the same Flask app, rendering a template. Keep the first version to three things: a session list with each one's edit ratio, a trend line of edit ratio over time (the actual drift signal — see §7), and a drill-down into a single session's before/after diff.

server.py (add-on)
@app.route("/dashboard")
def dashboard():
    with get_db() as conn:
        rows = conn.execute("SELECT * FROM sessions ORDER BY finalized_at DESC").fetchall()
    return render_template("dashboard.html", sessions=rows)

For the charts themselves, reuse the pattern already used across this project's own extra/explainer/DESIGN__*.html reports: dump the aggregates the dashboard route computes (daily/weekly mean edit ratio, edit-category counts) as a small JSON object embedded in the template, and draw them client-side with the same self-contained SVG bar-chart functions already written there — no charting library dependency, consistent look across every report this project produces.

Don't reach for a BI tool or a separate dashboard framework for a first version. A Flask template with one JSON blob and the SVG helpers already sitting in this repo gets you a working, versioned-in-git dashboard in under an hour — upgrade later only if the audience or scale actually demands it.

7 · Suggested ways to track degradation

"Degradation" here means the ambient AI's output quality getting worse over time — usually from a silent vendor-side model update, not from anything on your end. None of these need to be sophisticated to be useful; the value is in having any continuous signal, since right now the alternative is finding out from a clinician complaint.

  • Edit-rate over time, as a control chart. The edit_ratio already computed in §5, aggregated daily or weekly, plotted with a rolling mean and control limits (e.g. ±2–3 standard deviations of the trailing baseline). A sudden jump outside the band — especially one that lines up with a date rather than drifting gradually — is the single strongest signal of a silent model change.
  • Edit-category drift, not just edit volume. Run note_extractor.py/high_risk_checker.py-style categorization on every edit (was a drug name changed? a negation flipped? a whole differential added or removed?) and track the mix over time, not just the rate. A flat edit rate with a rising share of drug/negation corrections is a worse sign than a rising rate made up of stylistic rewording.
  • Canary transcripts, replayed on a schedule. Keep a small fixed set of transcripts (this project's own prim57 is exactly this kind of asset) and, wherever the vendor's interface allows a manual or API replay, run them through periodically and score the output against the existing checker pipeline — the same main.py/main2.py evaluation this project already runs, just repeated on a cadence instead of once.
  • CUSUM or EWMA on the edit-rate series rather than a plain moving average, if the control chart above turns out too noisy to act on — these are built specifically to catch a slow drift that a simple rolling mean smooths away for too long before flagging it.
  • Old-vs-new shadow comparison when the vendor ships a version bump you know about in advance (release notes, changelog) — run the same transcript through both and diff, rather than waiting to see if the edit-rate chart notices after the fact.
  • A one-click clinician quality signal alongside the automatic tracking (e.g. "this draft needed real fixes" vs "just tidied wording") — edit ratio alone can't distinguish a clinician's house style from an actual AI mistake, and this cheaply calibrates which is which over time.
  • Periodic human audit of a random sample, the same "double-check the flags" process used by hand throughout this project's labels_inferences/labels_extraction work — productionized as an ongoing weekly/monthly review of a small random slice rather than a one-off.

8 · Papers to read

There isn't much literature yet specifically on monitoring ambient clinical-documentation AI for drift — it's too new a product category. The closest, well-established body of work is general ML production-monitoring and concept-drift literature, plus one directly relevant LLM-specific study. Worth reading in roughly this order.

LLM-specific
Chen, Zaharia & Zou — "How Is ChatGPT's Behavior Changing over Time?" (2023)

Directly measures the same phenomenon this pipeline is built to catch: a hosted LLM's output quality and behavior changing release to release, with no announcement. The closest existing template for "canary prompts replayed on a schedule, diffed over time" in §7.

ML monitoring in production
Sculley et al. — "Hidden Technical Debt in Machine Learning Systems" (NeurIPS, 2015)

The standard reference for why a deployed ML system needs ongoing monitoring infrastructure at all, not just a one-time evaluation — makes the case for exactly this kind of capture pipeline as a first-class part of the system, not an afterthought.

ML monitoring in production
Breck et al. — "The ML Test Score: A Rubric for ML Production Readiness and Technical Debt Reduction" (IEEE Big Data, 2017)

A concrete checklist (Google's internal practice) for what "properly monitored" means for a production ML system — useful directly as a design checklist for §5/§6.

Concept drift
Gama, Žliobaitė, Bifet, Pechenizkiy & Bouchachia — "A Survey on Concept Drift Adaptation" (ACM Computing Surveys, 2014)

The standard survey of drift-detection methods (including CUSUM/EWMA-style approaches referenced in §7) — background for choosing a real detection method once the edit-rate series exists.

Dataset/distribution shift
Quiñonero-Candela, Sugiyama, Schwaighofer & Lawrence (eds.) — Dataset Shift in Machine Learning (MIT Press, 2009)

Foundational framing for why a model's real-world input distribution (here: real clinical encounters vs. whatever it was evaluated on) drifting is itself a cause of apparent "degradation" even with no model change at all — relevant context for interpreting a rising edit rate correctly.

Silent failure modes
D'Amour et al. — "Underspecification Presents Challenges for Credibility in Modern Machine Learning" (JMLR, 2020)

Explains why two model versions that look equally good on a benchmark can behave very differently in deployment — relevant to why a vendor's own eval numbers won't substitute for the canary-replay approach in §7.

Search these by author/title/year (Google Scholar or arXiv) rather than trusting a pasted link — exact URLs weren't verified here.
