2 · Modules/ — shared logic

Neither of these files know the extension or Flask exist — they're plain functions taking/returning plain data, same style as every other file in Modules/. That's what lets server.py import them directly and what let both be unit-tested from the command line while building this.

Modules/note_extractor.py — what to flag on a note

Pulls every medicine mention, negation, inference/impression, and (new) dose/frequency/duration/vital out of a note. No transcript needed — purely lexical/UMLS pattern-matching on the note text itself.

FunctionWhat it does
extract_note_content(note_text)Original entry point (still used by main2.py) — takes one blob of note text, detects SOAP section headers itself via SECTION_PATTERNS, returns every (type, section, detail, highlight) item.
extract_from_sections(sections)What the extension actually calls. Takes a {"Subjective": "...", ...} dict — the caller already knows each field's section from the UI, so this skips header-detection entirely and is more reliable for that case. Same output shape as above, plus the new "number" category.
_extract_medicines_from_line(line, section)Runs the shared QuickUMLS matcher, keeps only drug-semtype matches (DRUG_SEMTYPES from risk_taxonomy.py), drops common-word false positives via MEDICINE_DENYLIST.
_extract_numbers_from_clause(clause)New for the extension. Matches two shapes: NUMBER_PHRASE_RE (a number/word-number + unit, e.g. "2 tablets", "four times a day") and VITAL_SHAPE_RE (bare vital shapes with no unit word, e.g. "120/80", "37.5°C").
NEGATION_CUE_RE / INFERENCE_CUE_REPlain cue-word regexes (not medspaCy ConText) — tuned for this dataset's terse shorthand ("No SOB", "NKDA") rather than full conversational negation. See the module docstring for why.
_split_clauses(line)Splits one line into sentence-ish clauses on ./; + whitespace or newlines — the unit every cue-regex above is actually run against.

Modules/edit_diff_checker.py — before/after → critical or not

Given the AI's draft and the clinician's saved edit, judges each changed line critical or not. Reuses risk_taxonomy.classify_severity for the actual severity call rather than inventing a second scale.

FunctionWhat it does
diff_edit(note_before, note_after)The entry point. Line-level difflib.SequenceMatcher over the two notes; for every changed opcode block, calls _align_block then _classify_span on each resulting pair. Returns {similarity, edit_ratio, critical, changes: [...]}.
_align_block(old_lines, new_lines)Re-pairs lines within one difflib "replace" block by per-line text similarity, instead of treating the whole block as one span. Without this, several bullets changing in the same edit (dose and allergy status and follow-up) collapse into one opcode and only the highest-priority category gets reported — confirmed as a real bug while building this, see the function's own docstring.
_classify_span(old, new)Priority order: a drug present in old missing from new → "drug switch"; a negation cue present in one but not the other → "negation flip"; a dose/frequency/vital phrase differs → "number edit"; whole span new → "inserted sentence"; whole span deleted → "omitted detail"; otherwise → "reworded" (always non-critical — the "just tidied wording" case). Every branch except reworded is scored by risk_taxonomy.classify_severity; high/critical severities bucket to critical=True.
_drug_terms / _number_phrases / _has_negationThe three signals _classify_span diffs between old and new — each reuses the exact same matching rule as note_extractor.py so the two modules never disagree on "is this a drug"/"is this a number".

Both modules were unit-tested from the command line against realistic sample notes while building this (see the conversation this doc was generated from) — not run against the live DiSCaScribe page, since there's no browser-automation tool available to do that here.

3 · oogle api/server/server.py

Flask + CSV, no database. Three routes the extension/dashboard call, plus the storage/aggregation helpers behind them.

Routes

RouteWhat it does
POST /api/checkRuns every function in CHECKLIST_MODULES (just _run_note_extractor today) against the posted sections dict, concatenates their items, assigns each an id, returns {"items": [...]}. See §6 below for adding a second module.
POST /eventsPosted whenever the extension sees "Save" clicked. Joins the before/after section dicts into whole-note strings (_join_note), runs edit_diff_checker.diff_edit, writes a full-detail JSON file to data/sessions/, appends one summary row to data/events.csv.
GET /dashboardReads the whole CSV, computes the stat-tile numbers and _daily_aggregates, renders templates/dashboard.html.
GET /dashboard/session/<file>Serves one session's full JSON (transcript, both note versions, the changes list) for the dashboard's click-to-expand drill-down. os.path.basename()'d against path traversal.

Helper functions

FunctionWhat it does
_run_note_extractor(sections)Wraps note_extractor.extract_from_sections into the common checklist-item dict shape (type/section/text/highlight/color) every entry in CHECKLIST_MODULES must return.
_join_note(sections)Renders the four SOAP fields back into one plain-text note in fixed SOAP order, so diff_edit has a single string to compare rather than four.
_type_counts(changes)Turns a diff_edit result's changes list into {"type_drug_switch": n, ...} — one count per DETAIL_TYPES entry. Used both for a fresh CSV row and for migrating an old one (next row).
_ensure_storage()Creates data//the CSV with a header if missing. If the CSV already exists but is missing columns the current CSV_FIELDS expects (a schema upgrade, e.g. adding the per-type columns), it backfills every old row from that row's own session_file JSON rather than zero-filling or discarding history, then rewrites the CSV. Runs on every server start.
_read_events()csv.DictReader over the whole file — the dashboard's only read path, small enough at this scale that no database is needed.
_daily_aggregates(events)Groups rows by UTC calendar date into {date, count, avg_edit_ratio, critical, non_critical, types: {slug: count}} — exactly the JSON the dashboard's client-side SVG charts consume.

Module-level constants

NameWhat it's for
DETAIL_TYPES / TYPE_SLUGS / TYPE_COLUMNSThe six strings edit_diff_checker._classify_span can return, and their CSV-column/JS-key forms (spaces → underscores). Change this list and the CSV schema, the migration, the daily aggregates, and the dashboard's type chart all follow automatically — see §7.
CHECKLIST_COLORSThe four dot colors the floating widget uses — red/orange/blue/purple for medicine/number/negation/inference. A new checklist module reusing one of these four type values gets a color for free; a genuinely new type needs an entry here too.
API_KEYStatic dev placeholder, read from CAPTURE_API_KEY env var. Matches background.js's hardcoded copy — see the README's caveats section.

5 · oogle api/extension/

manifest.json

MV3. host_permissions covers both the DiSCaScribe origin (to inject content.js) and localhost:5000 (so background.js's fetch isn't blocked by the page's CSP — see the plan doc §3). content_scripts.matches is scoped to /consultations/* specifically, not the whole site.

background.js

ListenerWhat it does
onMessage: "CHECK_NOTE"POSTs {sections} to /api/check, returns {ok, items} to whichever content.js call sent it. return true keeps the message channel open for the async fetch.
onMessage: "NOTE_FINALIZED"POSTs the full before/after/transcript payload to /events.

popup.html / popup.js

The toolbar-icon popup. Reads/writes chrome.storage.sync.captureEnabled — the same flag content.js's in-widget toggle uses, so either one flips the other live.

6 · content.js — the big one

Everything that runs inside the DiSCaScribe page itself. Grouped the same way the file's own // ---------- section ---------- comments are.

Reading the note & transcript

FunctionWhat it does
readNoteSections()Edit mode: reads #soap-Subjective etc.'s .value directly (works regardless of which tab is active — the textareas stay mounted, just hidden). View mode fallback: collectViewLines below.
collectViewLines(root, out)Walks a <section> collecting each <p>/<li>'s own .textContent as one line. Deliberately not .innerText — that only inserts proper line breaks for an element that's actually rendered, so it silently glues every bullet into one run-on line both for a detached clone and for a section sitting in the currently-inactive tab's display:none panel. Fixed a real bug of exactly this shape while building this.
readTranscript()Anchors on the page's one <audio> element, walks up to its card, reads each turn's speaker label + bubble text via .textContent.
isEditMode()Just !!document.getElementById("soap-Subjective") — the presence check every edit-pass-tracking function is built on.

Jump-to / highlight

FunctionWhat it does
jumpToItem(item)Switches to the Clinical Note tab if needed, then: if in edit mode, textarea.setSelectionRange() on the matched substring (the textarea equivalent of "select and scroll to"); if in view mode, highlightInSection.
highlightInSection(sectionEl, needle)TreeWalker over text nodes to find needle, then uses the native Selection/Range API to select it (not a DOM-inserted <mark>, which risks fighting React's own reconciliation of that subtree) and scrollIntoView.

Checklist widget

FunctionWhat it does
createWidget()Builds the floating bubble + panel inside a ShadowRoot (isolates the widget's CSS from the page's Tailwind and vice versa), wires up the bubble/close/reset/toggle click handlers.
refreshChecklist()Reads the current sections; if there's no content at all, shows "No SOAP note detected" (renderNoSoap) instead of leaving a stale checklist showing; otherwise safeSendMessages CHECK_NOTE and re-renders on response.
itemKey(item)type|section|highlight — a content-based identity for a checklist item, used for the checked/green-state Set. Deliberately not the server's index-based item.id, which shifts every time the checklist regenerates; keying on content is what lets an unchanged item stay green across a refresh while a changed one resets.
renderPanel()Groups items by section, renders each as Type: highlighted text (not the full sentence), wires each <li>'s click to jumpToItem + mark checked.

Edit-pass capture

FunctionWhat it does
pollEditModeTransition()Called on every debounced mutation. On the false→true transition (edit mode just started), snapshots the current sections as editBaseline — the "og" version for this edit pass.
handleFinalize()Fired by the capture-phase click listener on document when the button titled "Save as the next note version" is clicked (capture phase so this runs before the page's own handler can save-and-swap the DOM). Builds the payload (session id from the URL, both section snapshots, transcript, timestamps), sends NOTE_FINALIZED, then clears every checked item and re-pulls the checklist once the page settles.

Context-invalidation guard

Reloading the extension from chrome://extensions mid-dev-session (normal workflow) breaks any already-open tab's connection to the old background worker. isContextValid()/safeSendMessage()/handleContextInvalidated() catch that and quietly disable the widget on the stale tab instead of throwing an uncaught error — the tab just needs a refresh to reconnect.

Boot

start()/stop() gate everything on chrome.storage.sync.captureEnabled, with a started flag so repeated off/on toggling doesn't stack duplicate MutationObservers or input listeners. chrome.storage.onChanged makes the toggle take effect live, no reload needed.

7 · Adding a checklist module

This is the "modules should be easy to add and remove like in main.py" part of the design — server.py's CHECKLIST_MODULES list is deliberately the same one-list-of-functions idiom as main.py's load_checker_modules().

  1. Write your logic as a plain module in Modules/ (like note_extractor.py) — a function that takes whatever input it needs and returns items.
  2. In server.py, write a thin wrapper matching _run_note_extractor's shape: takes the sections dict, returns a list of {"type", "section", "text", "highlight", "color"} dicts.
  3. Add its color to CHECKLIST_COLORS if it's a new type the widget hasn't seen (the four current ones — medicine/number/negation/inference — already have colors matching the original checklist sketch).
  4. Add the wrapper function to the CHECKLIST_MODULES list.
def _run_my_new_module(sections):
    items = []
    for finding in my_module.find_things(sections):
        items.append({
            "type": "my_type",
            "section": finding.section,
            "text": finding.text,
            "highlight": finding.highlight,
            "color": CHECKLIST_COLORS.get("my_type", "#666666"),
        })
    return items

CHECKLIST_MODULES = [
    _run_note_extractor,
    _run_my_new_module,
]

That's it — api_check() already concatenates every module's output and assigns ids, and content.js's widget already groups/colors/renders by whatever type/section/color values it's given, so nothing in the extension needs to change. To disable a module without deleting it, comment its line out of the list, same as main.py.

8 · Adding a new edit-diff detail_type

The critical/non-critical classifier is a single module (edit_diff_checker.py), not a list — you're extending its judgment, not adding a parallel one.

  1. Add your new case to _classify_span's if/elif chain in Modules/edit_diff_checker.py, returning a new detail_type string.
  2. If it should route through the existing severity rules, add that detail_type to Modules/risk_taxonomy.py's DETAIL_TYPES tuple and give classify_severity a branch for it. If it needs its own bespoke critical/non-critical rule instead, judge it directly in _classify_span the way "reworded" is (skip classify_severity entirely).
  3. Add the same string to server.py's DETAIL_TYPES list.

That third step is the only thing that needs to happen on the server side — TYPE_SLUGS/TYPE_COLUMNS, the CSV schema (auto-migrated by _ensure_storage on next server start), _daily_aggregates, and the dashboard's per-type chart (TYPE_SERIES in dashboard.html) all derive from that one list. You'll still want to add a color/label for it in dashboard.html's TYPE_SERIES array, the same way CHECKLIST_COLORS needs a new entry for a genuinely new checklist type.
