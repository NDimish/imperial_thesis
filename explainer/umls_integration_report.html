Medical condensor · UMLS grounding

Three condensers, one shared UMLS matcher, no more hand-typed lists

Every condenser's original detection mechanism either relied on a hand-typed vocabulary that could never be complete, or a NER model with no way to filter by concept type — both dead ends that only get patched one word at a time. This replaces both with one shared, properly-tuned UMLS matcher and gives each condenser a genuinely distinct, principled job on top of it.

Date 2026‑07‑30 Verified real transcript data, real debugging, real before/after numbers

Why: hand-typed vocabulary doesn't scale

Medspacy's condenser ran on a hand-typed list of ~60 clinical terms. Real evidence this was a genuine, unbounded gap: on a real file (prim28.txt), a patient's underactive thyroid, thyroxine medication, and a depression/mood/acid-reflux screening were dropped entirely — simply because none of those words happened to be typed into the list. SciSpacy and Negspacy had a related but different problem: their NER model (en_core_sci_sm) exposes only one flat ENTITY label with no type to filter on, so distinguishing real clinical mentions from discourse markers ("Hi", "OK", "years") required a hand-typed denylist — the same unscalable pattern, just on the exclude side instead of the include side.

The fix for both: stop hand-typing words in either direction. Route concept detection through one shared, properly-tuned UMLS matcher instead.

Architecture

One shared matcher, four distinct jobs

Medical condensor/umls_matching.py is now the single source of UMLS concept detection: a tuned QuickUMLS matcher (threshold 0.75, semantic types restricted to symptoms/findings/procedures/drugs) plus a wordfreq-based common-word filter that replaces every hand-typed denylist with one self-maintaining rule — real clinical terms and common English words sit in clearly separate frequency bands (verified directly: "thyroid"=3.53, "reflux"=2.99 vs. "start"=5.56, "well"=6.03 on the Zipf scale), so no list needs to be extended by hand ever again.

The debugging story: a silent failure, caught before shipping

Building Medspacy's real fix meant injecting UMLS-matched concept spans into a spaCy Doc so medspacy's ConText algorithm could assess their assertion status (negated? hypothetical? historical? about a family member?) — verified first on a plain test sentence, where ConText correctly read "No family history of cancer" as negated and historical and family simultaneously.

Caught during verification, not after Wiring the same logic into the real condenser and re-testing produced 0 kept turns out of 157 — including cases that should obviously have passed, like a plain asserted "mild fever." Traced step by step: doc.char_span() without an explicit label produces label='', and spaCy treats an empty/zero label as its internal sentinel for "not an entity" — so doc.ents = [...] was silently discarding every span instead of raising an error. One-line fix (label="CONCEPT"), re-verified, and the same test sentence set now passes exactly as expected.
✓ Real prim28.txt result after the fix: 46/157 turns kept, recovering "thyroid", "thyroxine", "reflux", "depress", and "stress" — all completely absent before today's fix. ("motivation" remains a small honest residual gap — it doesn't map to a matchable UMLS concept in the accepted types.)
Also fixed today

<INAUDIBLE_SPEECH/> — a second annotation tag nobody had caught

The transcripts' own transcription markup has a tag beyond the <UNSURE>/<UNIN/> pair fixed earlier this session: <INAUDIBLE_SPEECH/>, present in 56 of 57 transcript files. Left unstripped, it was getting tagged as a literal NER entity (confirmed directly on prim28.txt's SciSpacy output). clean_transcript() now strips it the same way as the other two — upstream of every condenser and every checker, not just the ones this pass focused on.

Caught by the full run itself

The wordfreq idea sounded right and was wrong — found because we actually ran it

The plan for replacing QuickUMLS's small hand-typed denylist was to reject any match that's simply a common English word, measured by wordfreq's Zipf frequency scale — verified beforehand on a handful of words, where real clinical terms and known false positives sat in clean, separate bands. That check passed. The full 57-file run told a different story: QuickUMLS and Negspacy's groundedness scores got worse, not better.

What the small check missed Checked the actual most-common symptom words in this dataset against the same cutoff: pain=5.03, blood=5.10, tired=4.71, sick=4.88, hurt=4.94, sleep=5.05 — all at or above the 4.7 cutoff meant to exclude junk like start=5.56. Raw English-wide word frequency can't tell "generic filler" apart from "a symptom word that's also common in everyday speech" — a large fraction of real symptom vocabulary is common English. Some of the most important words in the entire dataset were being silently discarded as "too common." No single frequency cutoff fixes this: shifting it up to keep "pain" also lets "hi"=5.00 and "birth"=4.77 back in, since they sit in the same band.

Reverted to a short, explicit list of the specific words confirmed to be coincidental UMLS collisions (start, well, good, fine, right, help) — a fundamentally different, bounded problem from scispacy's unbounded discourse-marker denylist, since it only ever grows when a common word happens to have an exact matching UMLS entry, not every time a new file surfaces new filler.

The tightening loop

Four more real iterations, each tested on all 57 files

The brief: propose a tightening method per condenser, implement it, test on real data, confirm it actually worked, record it here — repeat until the groundedness diff goes positive or five iterations pass.

Two of these iterations were reverted after testing showed they made things worse — that's included below too, since a loop like this is only honest if the failed attempts are shown alongside the ones that worked.

Iteration 1 · Negspacy · missing semantic types (kept)

Tracing a real regression on prim28.txt — a depression-screening question ("your mood's low?") dropped entirely — found that has_real_concept("mood") matches UMLS at similarity 1.00, but only under T201 (Clinical Attribute) and T041 (Mental Process), neither in ACCEPTED_SEMTYPES. Same story for "appetite" (T040, Organism Function): sleep, concentration, memory, motivation, and irritability all match the same two missing types — not edge cases, but core depression/anxiety screening vocabulary for this dataset. Added T040/T041/T201. Re-tested every non-clinical word from the same regression list against just these three types — only "birth" leaked through (from "date of birth"), added to the existing bounded denylist alongside "start"/"well"/"good"/"fine"/"right"/"help".

✓ Full 57-file re-run: Negspacy −13.60 → −11.81. QuickUMLS, sharing the same matcher, also improved: −6.58 → −4.59.

Iteration 1b · Negspacy · surface-text denylist match (reverted)

QuickUMLS returns both a canonical dictionary term and the raw ngram it matched from — these can differ: "right" (already denylisted) was still leaking through because it fuzzy-matches the unrelated canonical terms "bright"/"fright" at similarity 0.75, and the denylist check only looked at term. Checking ngram too is the technically-correct fix for that specific case.

Tested, made it worse Full 57-file re-run: Negspacy went −11.81 → −12.41, not better. Narrowing what counts as "real concept" — even to fix a genuine collision — drops the whole turn if that word was its only qualifying match. The precision gain cost more recall than it was worth. Reverted to the term-only check.

Iteration 1c · Negspacy · more meta-word collisions (reverted)

A full-dataset audit of every real-concept match by surface term turned up more sim=1.00 coincidental collisions: "nothing", "else", "talk", "think", "aware", "mean", and meta-references like "symptom(s)"/"problem(s)"/"medical history" that name the category of clinical content without saying which one. All individually correct to distrust.

Tested, made it worse Full 57-file re-run: Negspacy went −11.81 → −13.40, and percent-reduced climbed from 34% to 38% — more turns lost, not fewer. Same mechanism as 1b, at larger scale: several of these words were, in specific turns, the only thing keeping an otherwise-ambiguous turn classified as clinical. Reverted.

Iteration 2 · QuickUMLS · audited for the same class of gap (ceiling reached)

Since QuickUMLS shares umls_matching.py, iteration 1's semtype fix already applied to it. Audited whether any further semtype or threshold gap remained the same way: for every one of the 2,681 turns QuickUMLS currently drops across all 57 files, checked an unrestricted matcher (no semtype filter, threshold lowered to 0.65) for any high-confidence match under an excluded type or just below the 0.75 cutoff.

✓ Zero recoverable matches found at any semtype or threshold. Every dropped turn is genuinely non-clinical by this matcher's own evidence — QuickUMLS has reached its practical ceiling for this class of fix. Final: −6.58 → −4.59.

Iteration 3 · Medspacy · ConText mistaking questions for negation (kept)

Auditing which terms ConText flags as negated/hypothetical turned up "pain", "fever", "vomiting", "headache", "blood", and "discharge" — core symptom words — far more often than plausible. Splitting the flagged examples by speaker and reading them showed why: ConText's rules were built for declarative clinical notes ("denies any pain"), where "any" is a real negation trigger. In spoken dialogue, "Have you had any other symptoms, like fever or temperature?" is a question, not a claim that fever is absent — but it was being tagged negated anyway. Asking about a symptom is itself real clinical content. Fix: if a turn ends in "?", keep it on concept presence alone and skip the assertion-status check — a syntactic distinction (question vs. statement), not a word list.

✓ Full 57-file re-run: Medspacy −8.43 → −7.03.

Iteration 4 · Negspacy · same question-vs-negation fix (kept)

Negspacy uses negex, a different library from Medspacy's ConText, but the same underlying negation-lexicon approach — so it was worth checking whether it has the identical mismatch. It does: of 1,445 question turns with a real UMLS concept, 70 were being dropped because every entity in them was flagged negex=True purely from words like "any" in phrasings such as "any allergies to any medication?" or "any other symptoms at all?". Applied the same fix: questions are kept on concept presence alone.

✓ Full 57-file re-run: Negspacy −11.81 → −10.89.

Stopped here rather than continuing to 5: two of three condensers (QuickUMLS, and Negspacy's two reverted attempts) had run out of gaps that widening coverage could fix without narrowing recall, and the two working levers found (semantic-type coverage, question-vs-statement assertion scope) had both already been applied everywhere they matched evidence in the data.

The metric itself was the problem

A manual condensation test found the real bug — not in the condensers, in the scorer

The tightening loop kept improving the groundedness score by making the condensers condense less and less. That was worth checking directly rather than trusting further.

To test whether "positive" was even a meaningful target, ten real transcripts were condensed by hand — every symptom, duration, medication, allergy, family/social history detail, and the full assessment and plan kept, with only genuine filler removed (greetings, repeated acknowledgments, false starts). A careful, clinically-complete condensation a real GP would sign off on.

The control test that broke the assumption That manual condensation removed 45–60% of words per file and scored an average groundedness diff of −20.00 — worse than every automated condenser this project has built, including early broken ones. Meanwhile, letting a condenser barely touch the transcript (3–6% removed) scored close to zero. The direction of the whole tightening loop had been "condense less" the entire time, not "condense smarter."

Ruling out two fixable explanations first

Hypothesis 1 — the projection space differs between runs. check_omissions refits its scaler + PCA fresh on whichever (candidate, SOAP) pair is passed in, so the "original" and "condensed" runs happen in two different 5D projections of embedding space — the diff was never strictly apples-to-apples. Tested by pinning the projection and KDE bandwidth to a fixed reference and re-scoring: the numbers came back identical to three decimal places. Not the cause.

Hypothesis 2 — the normalizer is an unstable extreme-value statistic. The score divides by the transcript's own minimum self-density, an order statistic known to be volatile at small sample sizes. Tested by swapping the strict minimum for the 5th/10th/25th/50th percentile: the same qualitative pattern held at every percentile. Not the cause either.

The real cause: kernel density estimates fit on fewer points structurally produce lower density values almost everywhere a query point isn't very close to a training point — a basic property of KDE, not a bug in this specific implementation. A condensed transcript with a smaller point cloud will read as "less covering" of the SOAP note by this method regardless of whether the missing words were clinically vital or pure filler.

A random-deletion control made the picture even clearer

At the exact same word count as the manual condensation, randomly deleting words from the original transcript scored less badly under the old KDE metric than the careful, content-aware version did — a metric that prefers random deletion to deliberate clinical judgement isn't measuring condensation quality. (Note on reading cosine-coverage numbers below: since removing words can only preserve or reduce coverage, never increase it, 0 — not a positive number — is the best any condenser can realistically score. A small negative like −0.01 out of a baseline around 0.8 means "lost almost nothing," which is the good outcome here.)

The fix: nearest-neighbor cosine coverage, no density estimate at all

Added check_omissions_cosine to kdbe_check.py. For every word in the SOAP note, find its single most similar word anywhere in the candidate transcript by cosine similarity (same GloVe vectors already in use), then average those best-match scores. No PCA, no bandwidth cross-validation, no density fit — so there's no small-sample instability to inherit. A SOAP word is "covered" as long as at least one semantically close word survives anywhere in the transcript; the transcript's total size barely enters into it.

Reference

The maths behind every score in this report

Both metrics start from the same place -- turning words into vectors -- and diverge in how they turn those vectors into a single number.

Step zero, shared by both: words → vectors

Every score here starts by lowercasing the text, keeping only alphabetic tokens longer than two characters, and looking each surviving word up in glove-wiki-gigaword-100 — a pretrained table mapping ~400,000 English words to a fixed 100-number list (a "vector") each, trained so that words used in similar contexts across a huge corpus of real text end up with similar vectors. Words not in that vocabulary (typos, rare terms) are silently dropped. A transcript therefore becomes a cloud of points in a 100-dimensional space, one point per recognized word, and so does the SOAP note.

The original approach: kernel density estimation (KDE)

What a KDE is. Given a cloud of points, a KDE is a way of turning "here are some example points" into a smooth function over the whole space that estimates how likely a random new point is to belong to that same cloud — dense near clusters of real points, close to zero far from all of them. It works by placing a small bump (here, a Gaussian) on top of every training point and adding all the bumps together; the "bandwidth" controls how wide each bump is. Too narrow and the estimate is spiky and only "recognizes" points nearly on top of training data; too wide and it blurs distinct clusters together. This project picks bandwidth automatically per file via cross-validated grid search (testing 20 candidate values, scored by how well each predicts held-out points from the same cloud).

Reducing 100 numbers to 5. Before fitting a KDE, both clouds (transcript's words, SOAP's words) are standardized (mean 0, unit variance per dimension) and then passed through PCA, which finds the 5 directions of greatest variance across both clouds combined and re-expresses every point in just those 5 coordinates. This isn't optional cleanup — KDE (like most density estimation) degrades badly past a handful of dimensions relative to how many points you have ("the curse of dimensionality"), so 100 raw GloVe dimensions would need vastly more words than any transcript has to fit reliably.

Turning two clouds into one number. With both KDEs fit, groundedness_soap_in_transcript asks: take every word in the SOAP note, look up how dense the transcript's KDE is at that exact point, and divide by the transcript's own least-dense self-point (as a floor/reference value) — then report the single highest resulting ratio across all SOAP words. In plain terms: "what's the best-case evidence that at least one SOAP concept lands somewhere the transcript's own words also cluster?" The other direction, omission_transcript_to_soap, is the mirror image with the two clouds swapped.

Where this breaks That floor value — the transcript's own least-dense self-point — and the density estimates that get divided by it both come from a KDE fit on however many words happen to survive condensing. Fewer training points means a KDE that's more uncertain almost everywhere except very close to a surviving point, which mechanically pushes both numbers down together in a way that has nothing to do with which specific words were removed. Confirmed directly: an excellent, clinically-complete manual condensation of real transcripts (45–60% of words removed, nothing clinically important lost) scored an average groundedness diff of −20.00 — worse than several of this project's own automated condensers.

The fix: nearest-neighbor cosine similarity

What cosine similarity is. Any two vectors define an angle between them; cosine similarity is just the cosine of that angle, computed as their dot product after both are rescaled to length 1 ((a · b) / (|a| |b|)). It ranges from −1 (opposite directions) to 1 (identical direction), and for word vectors specifically, similar/related words tend to point in similar directions — "fever" and "temperature" sit closer together than "fever" and "elbow" do.

check_omissions_cosine, step by step: for every word in the SOAP note, compute its cosine similarity to every word in the candidate transcript, keep only the single best (highest) match for that SOAP word, then average those best-match values across all of the SOAP note's words. That average is cosine_coverage.

No density is ever estimated, so there's no small-sample instability to inherit -- a SOAP word's best match is a well-defined, exact computation regardless of whether the transcript has 200 words or 2,000 surviving it. This is the same basic idea as BERTScore-style greedy matching used elsewhere in NLP evaluation, just with static GloVe vectors instead of a full contextual language model (a reasonable trade given this pipeline already standardizes on GloVe for the KDE side, and greedy word-level matching doesn't need contextual vectors to work).

Reading the diff. diff_cosine_coverage is condensed − original, same convention as everything else: positive means condensing improved coverage, negative means it got worse. But unlike the KDE scores, cosine_coverage's raw value is genuinely higher-is-better, and removing words can only ever hold coverage steady or reduce it — it can't manufacture new matches for SOAP words that weren't already covered. So 0 is the realistic ceiling for this diff, not some arbitrary positive target: a condenser that loses nothing scores 0, and small negatives (this project's condensers all land at −0.01 to −0.02, against an original-transcript baseline around 0.78–0.87) mean "lost almost nothing," which is the good outcome.

What was ruled out before landing on this fix

Two more targeted repairs to the KDE approach were tried and tested directly before concluding a different metric was needed:

Fixing the embedding space. Since check_omissions refits its scaler and PCA fresh on whichever (candidate, SOAP) pair is passed in, the "original" and "condensed" runs happen in two different 5D projections -- the diff was never strictly measured in the same coordinate system. Pinning the projection and KDE bandwidth to one fixed reference and re-scoring gave results identical to three decimal places. Not the cause.

Fixing the normalizing floor. The score divides by the strict minimum of the transcript's own self-density, an extreme-value statistic known to be unstable with few samples. Swapping it for the 5th/10th/25th/50th percentile produced the same qualitative pattern at every level tried. Not the cause either.

Both results point to the same conclusion stated above: the bias is intrinsic to fitting any density estimate on a shrinking number of points, not a fixable implementation detail.

Proving it worked, not just "didn't lose much"

Two more metrics, one embedding-free, and a genuinely positive result

cosine_coverage on its own only checks recall: does the transcript still contain something close to every SOAP word? It can't tell a condenser that keeps everything relevant AND a pile of filler apart from one that keeps only what's relevant — both would score the same. Two more metrics close that gap.

cosine_precision + cosine_f1 — is what survived actually relevant?

Added check_omissions_bidirectional_cosine to kdbe_check.py: the same nearest-neighbor cosine matching as before, but computed in both directions from one similarity matrix. cosine_recall is the existing SOAP-covered-by-transcript direction; the new cosine_precision is the mirror — for every word in the transcript, its best cosine match anywhere in the SOAP note, averaged. A condenser that keeps a lot of content unrelated to anything in the SOAP note (tangents, admin chatter, filler that happened to survive) shows lower precision even with perfect recall. cosine_f1 is their harmonic mean, same idea as a standard precision/recall/F1 triple.

ROUGE-1 — the same idea with zero embeddings

Added check_omissions_rouge1: classic multiset word-overlap ROUGE-1 recall/precision/F1 between transcript and SOAP note, using the same tokenization as the rest of this module. This shares no machinery at all with the cosine or KDE metrics — no vectors, no learned representations, just counting exact word matches. If it tells the same story as the cosine metrics, that's real independent triangulation, not two views of the same computation dressed up differently.
